# Bot：目标、功能与使用

一个常驻在 Jarvis 里的 Bot。你给它发消息，它拆成条目、派执行者去办，办完回来告诉你，卡住问你一句。

本文是产品定义，不是实现方案。实现见 `docs/bot-architecture.md`，冲突处以那份为准。

## 一、目标

把"一堆散活"变成"一个能托付的对象"：你说一句话，它接住、排开、派人做、回来交账。

做成与否只看三条：

1. 一次交 12 件混在一起的活，派活那条指令在所有活干完之前就返回。
2. 每件的结果都能在同一条对话里看到，并能点开追到某个项目里的那次运行记录。
3. Jarvis 关掉队列就不跑；重启后被中断的条目只被点名一次，不擅自重跑。

## 二、功能

### 对话

| # | 功能 | 说明 |
| --- | --- | --- |
| 1 | 单条长期会话 | 你和它的所有事在同一条对话里，可以随时插话 |
| 2 | 忙时你的消息优先 | 正在跑的不停，你的话插到汇报前面 |
| 3 | 它只说不做 | 不改文件、不跑命令；活全部由执行者做 |
| 4 | 一次只问一个问题 | 卡片式，允许 / 不允许；问出去不阻塞 |

### 任务

| # | 功能 | 说明 |
| --- | --- | --- |
| 5 | 说话即入队 | 一条消息可以含多条，拆成条目；入队后立刻在回复里列出拆分，未开工的可以改或跳过 |
| 6 | 条目状态 | 待做 / 进行中 / 完成 / 失败 / 跳过 / 中断 |
| 7 | 并发上限 | 全局默认 2，可调 |
| 8 | 重试、跳过、整批叫停 | 整批叫停要确认，已在跑的杀掉，未完成留下 |

### 执行

| # | 功能 | 说明 |
| --- | --- | --- |
| 9 | 一条一个执行者 | 在该条目所属项目里跑独立会话，一条只属于一个项目 |
| 10 | 结构化交账 | 执行者结束时必须申报：完成 / 需要帮助 / 无变化，加一句话结论与证据 |
| 11 | 过程不外泄 | 执行者的工具过程不进主对话；点开条目才看日志 |
| 12 | 不污染项目 | 执行者的会话不出现在项目会话列表、搜索、清理里 |

### 汇报

| # | 功能 | 说明 |
| --- | --- | --- |
| 13 | 批量汇报 | 单条完成只动看板；攒满 3 条、或 2 分钟、或该批最后一条，才说一句 |
| 14 | 失败单报 | 失败立即出现一行结论；同一原因 5 分钟内合并成一条 |
| 15 | 停住只提示不杀 | 超过安静时限标「N 分钟无输出」，到 2 倍阈值才说一句 |
| 16 | 说完才算完 | 结束那一轮必须说出结果；说出来之前状态仍是进行中 |

### 询问与授权

| # | 功能 | 说明 |
| --- | --- | --- |
| 17 | 只对会改目标的动作提问 | 整批停、整类跳过、删数据、把规矩写进记忆 |
| 18 | 未决不阻塞 | 未决期间已在跑的继续，其他条目照常开工 |

### 定时

| # | 功能 | 说明 |
| --- | --- | --- |
| 19 | 一次 / 周期 | 到点叫醒它来排；周期最短 5 分钟 |
| 20 | 错过不补跑 | Jarvis 关着就不跑；重启最多叫醒一次，由它决定 |

### 记忆

| # | 功能 | 说明 |
| --- | --- | --- |
| 21 | 一份笔记 | 只记职责与固定做法；只有你明确说过的规矩才写入，它不自己总结 |
| 22 | 记进度不算记忆 | 进度一律看队列，笔记里不写完成数 |

### 界面

| # | 功能 | 说明 |
| --- | --- | --- |
| 23 | 侧边栏 Bot 行 | 在项目之上。名字 + 状态：进行中 3 / 空闲 / 失败 1 / 已停 |
| 24 | Bot 页 | 复用会话时间线；顶部一行看板：待做 · 进行中 · 失败 · 并发 |
| 25 | 条目列表与日志 | 点失败或正在查的条目，看那一本条目的日志与结论 |

### 不做

云电脑、外部聊天软件、群聊与多 Bot 互派、技能库、预算核算、复核关卡、会等待回答的确认框、把 Bot 或执行者塞进隐藏项目。

## 三、使用起来的样子

**09:12 建档**
侧边栏项目上方出现「Bot」分组，空态一行「还没有 Bot」。点「新建 Bot」，两个字段：`名字`、`职责`，按钮「创建」。进去是一条空对话，输入框占位「说任务，可以一次多条」。

**09:30 交 12 件**
你贴 12 行。它拆成 12 个条目，回一句：

```text
12 条，开 3 条
```

看板变成 `待做 9 · 进行中 3 · 失败 0 · 并发 3`。

**09:34—09:52 陆续完成**
单条完成只改看板数字，时间线不新增行。攒到第 3 条时它说一句：

```text
A、B、C 完成。D 失败：tests 目录不存在。
```

**09:41 插话**
你打「先做 5、6」。消息立刻进时间线，在跑的 3 条不停。它回：

```text
5、6 先开，已跑的 3 条不停
```

**10:05 它要你定夺**
它想跳过后 4 条，先在对话里放一张卡：

```text
跳过 4 条：overtime 相关。已在跑的 2 条继续。
[允许] [不允许]
```

你不回，队列照常跑。

**10:20 一条没动静**
条目旁边标 `41 分钟无输出`，看板不变，它不说。到 70 分钟才说一句：

```text
3 号 70 分钟无输出，还在跑
```

**11:51 交完**
最后一条结束，它说：

```text
12 条：9 完成、2 失败、1 跳过
```

**13:10 回来**
侧边栏 `失败 2`。进 Bot 页，顶上只有一行 `9 完成 · 2 失败 · 1 跳过` 和「看失败」。条目列表里点开一条，是那次运行的日志和结论，底部「重试」「跳过」。点重试，它回：

```text
2 条重试，已开
```

## 四、调研记录

### 看过什么

| 对象 | 看法 | 直接采信的部分 |
| --- | --- | --- |
| Grok Bot 官方文档 | 7 个页面，含 bots / routines / security / notifications | 消息优先于后台、审批三键、Needs attention 与 Unread 分开、例行最短 5 分钟 |
| Comma（源码，222 MB，8 次提交全是自动同步） | 文档比代码准；README 的"自我复核"没有对应实现 | 任务即会话、结构化申报、汇报预算（30 分钟间隔 / 24 小时 5 次）、重启从事实重算 |
| Paperclip（源码，180 张表，`issues.ts` 14,284 行） | 公司模型不能照搬；单个文件就是 1.4 万行 | 心跳用 `lastHeartbeatAt` 条件更新当租约、驳回必须带评论、结果必须带 `question` 字段 |
| dsh-superagent（9 篇设计文档） | 教学样本，无沙箱、未审计；但授权与注意力两条写得最清楚 | 只在人必须行动时说话、一次一个问题、等待必须结构化而非模型自述、人永远不排在 agent 后面 |
| OpenClaw / Hermes | 定时与降噪做得最完整，但有 tick 被吞、cron 输出不回灌的 issue | 触发前置条件不满足时零 token、静默令牌、过期任务重排不重放、失败按错误签名合并告警 |
| Jarvis 仓库 | 已有：会话队列、注意力状态、事件扇出、时间线、隐藏会话前缀 | 复用时间线与流；没有任务与调度 |

### 路上遇到的几件事

1. **子代理没有联网工具。** 规划类子代理的工具被限死成只读本地文件，第一轮五个里有三个直接拒答并要求改派；改成主代理抓页面、执行类子代理用 shell 抓仓库，才拿到原文。这本身是个可用性信号：真要长期做调研，抓取和判断得分开。
2. **星数不可信。** 这一批仓库大半是 8 月后批量建仓，名字互相抢；能装能跑的很少。
3. **Comma 的"做完"定义是对的。** 它不接受自然语言里的"做完了"，只认结构化申报加证据；我们直接照抄这条。
4. **Paperclip 的规模是一面镜子。** 它把"公司"需要的东西都建了：目标、项目、预算、复核阶段。一个人用，真正需要的只有四张表，剩下的都是给多租户兜底的。
5. **上一版实现踩的两个坑。** 另一条会话用"每条约一个 CLI 进程 + 解析 stdout 里的一行结果"的方式跑通过，代价是：工人不知道要打那一行（靠主机拼进任务正文），Pi 落盘的会话文件名带时间戳前缀（路径对不上）。这两处都是真实运行时才暴露的。
6. **Jarvis 的真实约束。** 现有会话必须先有项目；`steer` / `followUp` 只会入队、不会开跑，空闲时叫醒必须用 `prompt`；注意力状态由会话服务写，调度器改不了；流式身份是 `workspaceId + sessionId`。这几条决定了 Bot 不能靠"复用项目会话"糊过去。

### 因此改掉的方案

| 原方案 | 改成 | 原因 |
| --- | --- | --- |
| 工人是独立 CLI 进程，靠 stdout 一行交账 | 工人在进程内起独立会话，靠会话结束事件交账 | 省掉结果行协议与文件名对不上的坑；取消只需 abort |
| 汇报随每条完成冒一句 | 单条只动看板，攒 3 条 / 2 分钟 / 该批结束才说 | 12 条会有 12 段汇报，比不汇报更烦 |
| 未决问题靠"下一条消息里提到 questionId" | 卡片按钮 | 自由文本匹配会静默失败，人以为停了其实没停 |
| 作业与条目两套状态机 | 只有条目状态，批次是字段 | 一份事实两个写者，必然打架 |
| 每作业并发、暂停、恢复、换工人 | 一个全局并发 + 重试 / 跳过 / 叫停 | 单用户没有需要这些旋钮的场景 |

### 还剩的风险

1. **进程内工人和 Bot 抢同一个模型额度。** 并发默认 2 是为了先别把自己卡住，真实延迟下需要实测再定。
2. **"停住"的判定。** 30 分钟对慢任务仍可能误判，所以只提示不杀；阈值是否合适只能靠用。
3. **拆条目的质量。** 12 行混活的拆分靠模型，拆错就只能靠你改；不做规则的自动重拆。
4. **笔记会腐化。** 只有你明确说的规矩才写，长期看笔记可能互相矛盾，需要在界面里能整份改。
